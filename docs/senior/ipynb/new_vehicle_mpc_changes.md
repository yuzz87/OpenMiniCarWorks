# 新しい実機向けMPCコード変更記録

更新日: 2026-07-13

## 目的

先輩のPython Notebookで使用していたMPCを、新しいRCカーの実測座標、車両特性、通信仕様、安全条件へ段階的に適合させる。

現在の実験目標は次のとおり。

- 参照直線に沿って前進する。
- 指定した目標位置で停止する。
- 参照状態、実測状態、MPC要求入力、実車適用入力を区別して記録する。
- シミュレーション結果と実車結果を比較する。

詳細なNotebook静的解析は[`notebook_cell_review.md`](notebook_cell_review.md)を参照する。

## ファイル運用方針

- 先輩のオリジナルNotebookは直接変更しない。
- 新しい実機向けコードは[`new_vehicle_mpc.py`](new_vehicle_mpc.py)へ実装する。
- 変更は一項目ずつ行い、実装済み・未実装を明記する。
- 角度はラジアン、距離はメートル、速度はメートル毎秒を使用する。
- 実機固有の速度、操舵、PWM、GPIO値を黙って変更しない。
- ハードウェア出力は、PC側検証と安全確認が完了するまで追加・有効化しない。

## 現在確認されている主な問題

1. MPC参照開始状態は`[0 rad, 0 m, -2 m, 0 rad]`で固定されている。
2. 保存グラフ上の実測開始位置は概算で`(-1.05 m, 0.18 m)`であり、約`2.42 m`ずれている。
3. MPCは車速`-0.1 m/s`まで許可するが、Raspberry Pi側は負速度を`0.0 m/s`へ安全制限する。
4. 参照速度`0.4 m/s`は、現在の実車安全上限`0.30 m/s`を上回る。
5. `SimTime = 7 s`では`goal_dist = 4.0 m`へ到達せず、参照終端は約`2.796 m`になる。
6. MPC第2入力は前輪舵角ではなく、前輪舵角速度`omega [rad/s]`である。
7. Simulink内の`[v, omega, φ, x, y, ψ]`から`[raw1, raw2, raw3]`への変換は未確認である。

## 変更1: 参照軌道を初期方位へ対応

### 状態

**実装済み**

### 対象

[`new_vehicle_mpc.py`](new_vehicle_mpc.py)の`make_reference_traj()`。

### 変更理由

先輩コードは参照直線を常にグローバル座標の`x`正方向へ生成していた。

```python
x_pos = x0 + s
y_pos = y0
phi = 0.0
```

Motive上で実車を固定参照の開始位置・方位へ物理的に合わせられない場合に備え、受信した初期方位に沿う参照直線も生成できるようにする。Motiveで毎回正確に合わせる運用では、この任意機能を使用しなくてもよい。

### 実装した式

```text
s(t) = min(v_ref × t, goal_dist)

x_ref(t) = x0 + s(t) cos(phi0)
y_ref(t) = y0 + s(t) sin(phi0)
phi_ref(t) = phi0
psi_ref(t) = 0 rad
```

実装コードの中心部分は次である。

```python
distance = np.minimum(v_ref * times, goal_dist)

reference[0, :] = phi0
reference[1, :] = x0 + distance * np.cos(phi0)
reference[2, :] = y0 + distance * np.sin(phi0)
reference[3, :] = 0.0
```

### 方位と進行方向

| `phi0` | 参照の進行方向 |
|---:|---|
| `0 rad` | `x`正方向 |
| `π/2 rad` | `y`正方向 |
| `π rad` | `x`負方向 |
| `-π/2 rad` | `y`負方向 |

### 状態順序と単位

```text
reference = [φ, x, y, ψ]
```

| 状態 | 意味 | 単位 |
|---|---|---|
| `φ` | 車体方位 | rad |
| `x` | 位置 | m |
| `y` | 位置 | m |
| `ψ` | 前輪舵角 | rad |

### 追加した入力検査

- `t_eval`が1次元か。
- `t_eval`が空でないか。
- 時刻が有限かつ非負か。
- `v_ref`、`goal_dist`、`x0`、`y0`、`phi0`が有限か。
- `v_ref`が非負か。
- `goal_dist`が非負か。

### 互換性に関する注意

現在の既定値は先輩コードとの互換性のため残している。

```text
v_ref = 0.4 m/s
goal_dist = 4.0 m
x0 = 0.0 m
y0 = -2.0 m
phi0 = 0.0 rad
```

これらは新しい実車向けに承認済みの値ではない。現在の実車安全上限や実測開始姿勢へ適合させる処理は、後続の変更で行う。

この変更だけでは、呼び出し側が既定値を使うため実行時の参照軌道はまだ変わらない。

### Notebookへ反映するときの範囲

`new_vehicle_mpc.py`の全80行をNotebook全体へ貼り付けない。

先輩Notebookで次を検索する。

```python
def make_reference_traj(...):
```

この関数が入っているセルだけを、次のimportへ置き換える予定である。

```python
from new_vehicle_mpc import make_reference_traj
```

Notebookと`new_vehicle_mpc.py`が同じディレクトリにあることが前提である。旧`make_reference_traj()`をimportより後で実行すると旧関数が上書きするため、旧関数セルは実行しないか、セル自体をimportへ置き換える。

現在は実際の`.ipynb`ファイルがないため、Notebookへの置き換えはまだ行っていない。

### 表記の整理

計算内容は変えず、`new_vehicle_mpc.py`の説明、コメント、例外メッセージを日本語へ変更した。

## Motiveで初期姿勢を合わせる運用について

Motiveを見ながら、実車を毎回次の固定参照開始状態へ物理的に合わせる場合、受信初期姿勢から参照全体を自動シフトする変更は必須ではない。

```text
[REF_START] = [φ, x, y, ψ] = [0 rad, 0 m, -2 m, 0 rad]
```

この運用では、従来どおり次の呼び出しを維持できる。

```python
x_ref = make_reference_traj(t_eval)
```

`new_vehicle_mpc.py`へ追加した`phi0`対応は後方互換であり、既定値では先輩コードと同じ参照を生成する。

ただし、Motive画面で見える値と、Simulink経由でPythonが受け取る値が同じとは限らない。保存済みグラフでは実測開始位置が概算`(-1.05 m, 0.18 m)`、参照開始位置が`(0 m, -2 m)`だったため、過去の実験時点では一致していなかった。

自動シフトの実装前に、実際の受信値を確認する。

```text
[FIRST_RX] (flag, φ, x, y, ψ)
期待値       (1,    0, 0, -2, 0)
単位              rad m   m rad
```

初期位置をMotiveで合わせる運用では、自動的に参照を実車位置へ移動するより、開始条件が許容範囲外ならMPCを開始しない検査を追加する方が、先輩実験との比較と再現性に適している。

## 初期位置変更に関する決定

今回は、受信した初期姿勢へ参照軌道を自動シフトする変更をNotebookへ適用しない。Motiveを使って実車を固定参照開始状態へ合わせ、実験結果から原因を確認する。

`new_vehicle_mpc.py`の任意機能は別ファイル内に残るが、既存Notebookからimportせず、現在の実験動作には使用しない。

## 次の変更候補: 入力速度制約

先輩Notebookの制約条件セルにある次の部分が対象である。

```python
# 入力: [v, omega]
u_lb = [-0.1, -0.70]
u_ub = [1.2, 0.70]
```

配列の第1要素が車速`v [m/s]`、第2要素が前輪舵角速度`omega [rad/s]`である。

現在のコードは次を許可する。

```text
-0.1 m/s <= v <= 1.2 m/s
```

一方、現在の実車受信側は負速度を`0.0 m/s`へ制限し、主に`0.30 m/s`を安全上限としている。そのため、将来の変更候補は概念的に次である。

```python
u_lb = [0.0, -0.70]
u_ub = [0.30, 0.70]
```

ただし、この変更は今回の原因確認実験より前には適用しない。`v_min = 0.0 m/s`にするとMPCが本来出していた負速度が見えなくなり、座標・方位・Simulink変換の問題を隠す可能性がある。

実験では、ハードウェア出力の安全制限を維持したまま、MPC要求速度`U_log[:, 0]`とRaspberry Pi受信ログの`negative_speed`を記録する。原因確認後、前進専用実験であることを確定してからMPC速度制約を変更する。
