# ellipse_run 実機接続・動作確認手順

## 目的

`ellipse_run`をRaspberry Pi 4と実車へ接続し、次の処理を使った楕円走行を確認する。

```text
odometer -> localizer -> reference_path -> pure_pursuit -> car_driver
```

この手順ではLiDARとカメラを使用しない。自己位置は、タイヤエンコーダで測定した
移動距離と指令操舵角を使うデッドレコニングで推定する。

## 現在の構成と仮定

| 項目 | 設定 |
| --- | --- |
| 車体 | Tamiya TT-02系 |
| 制御PC | Raspberry Pi 4 |
| 駆動 | ESC + モーター |
| 操舵 | RCサーボ |
| エンコーダ | A/B相、36歯 |
| タイヤ直径 | `0.066 m`（仮の校正値） |
| ホイールベース | `0.250 m`（仮の校正値） |
| 最大操舵角 | `28 deg`、約`0.489 rad`（仮の校正値） |
| 制御周期 | `50 Hz` |
| 目標楕円 | X半径`2.0 m`、Y半径`1.2 m` |

ホイールベース、タイヤ直径、操舵角、サーボ中立、ESC中立および駆動パルス幅は
車両固有の校正値である。実測せずに他の車両へ流用しないこと。

## 安全上の前提

- 最初の確認は駆動輪を床から完全に浮かせて行う。
- 車両の主電源をすぐ切れるようにし、物理的な電源遮断手段を手元に置く。
- Raspberry Pi、エンコーダ、BECまたはサーボ電源、ESC信号のGNDを共通化する。
- モーターや操舵サーボをRaspberry PiのGPIOまたは`3.3 V`ピンから給電しない。
- Raspberry PiのGPIOは`3.3 V`ロジックである。`5 V`のエンコーダ出力を直接入力しない。
  エンコーダ仕様を確認し、必要ならレベル変換を使用する。
- コネクタの線色だけで端子順を判断しない。部品資料または測定したピン配置を使う。
- `THROTTLE_DRIVE_US`、操舵範囲、パルス幅制限を確認なしに拡大しない。
- 床上走行は、浮かせた状態で中立、回転方向、操舵方向、エンコーダ方向、
  `Ctrl-C`停止をすべて確認した後に行う。

## 配線

`run_ellipse.py`はBCM GPIO番号を使用する。

| 機能 | BCM GPIO | Raspberry Pi物理ピン |
| --- | ---: | ---: |
| 操舵サーボ信号 | 17 | 11 |
| ESC信号 | 18 | 12 |
| エンコーダA相 | 22 | 15 |
| エンコーダB相 | 27 | 13 |

電源を切った状態で配線し、信号線とGNDの導通および短絡がないことを確認する。
サーボとESCの電源方法、エンコーダの電源電圧、コネクタ端子順は各部品の仕様に従う。

## 1. Raspberry Piへ必要なソフトウェアを用意する

Raspberry Pi OS上で、pigpio、RPi.GPIO、NumPyを使用できる状態にする。
パッケージ名は使用中のOSリリースで確認すること。一般的な導入例は次のとおり。

```bash
sudo apt update
sudo apt install pigpio python3-pigpio python3-rpi.gpio python3-numpy
```

Matplotlibは任意である。インストールされていない場合、走行後のPNG生成だけが省略される。

## 2. PCシミュレーションを確認する

実機へ信号を出す前に、`run_ellipse.py`の設定が次のままであることを確認する。

```python
use_hardware = False
```

リポジトリのルートで構文を確認する。

```bash
python3 -m py_compile scripts/ellipse_run/*.py
```

生成ファイルが`ellipse_run`内へ保存されるよう、そのディレクトリから実行する。

```bash
cd scripts/ellipse_run
python3 run_ellipse.py
```

次を確認する。

- 例外を出さずに1周分が終了する。
- `pose_log.csv`が生成される。
- Matplotlibがあれば`ellipse_track.png`が生成される。
- 起動時に表示される経路最小半径が車両最小旋回半径を下回っていない。

シミュレーションの推定軌跡は、ローカライザと同じ運動モデルで生成した移動量を使う。
したがって、実車の位置推定精度や追従性能を独立に検証するものではない。

## 3. 車両パラメータを設定する

`run_ellipse.py`の次の値を実測結果に合わせる。

```python
WHEELBASE = 0.25
WHEEL_DIAMETER = 0.066
N_TEETH = 36
MAX_STEER_DEG = 28.0

STEER_NEUTRAL_US = 1500
STEER_RANGE_US = 400
STEER_SIGN = 1
THROTTLE_NEUTRAL_US = 1500
THROTTLE_DRIVE_US = 1440
```

`MAX_STEER_DEG`は度、制御内部の操舵角はラジアンである。

現行オドメータはA相の立ち上がりだけを数え、36カウントをタイヤ1回転として扱う。
タイヤ直径が`0.066 m`の場合、1回転の計算距離は次のとおり。

```text
pi * 0.066 m = 約0.207 m
```

車体を前進方向へ動かしたとき、オドメータ距離が正になる必要がある。負になる場合は
A/B相の接続と方向判定を確認し、解決するまで自律走行へ進まない。

`STEER_SIGN`は操舵方向を反転する設定である。正の操舵指令と実際の旋回方向が逆の場合のみ、
機械的な接続とGPIOを確認したうえで`-1`へ変更する。

`THROTTLE_DRIVE_US = 1440`は、このリポジトリで想定しているESCの前進値であり、
すべてのESCに共通ではない。ESCの取扱説明書に従って中立、前進方向、アーミング手順を確認する。

## 4. pigpioを起動する

実機出力にはpigpioデーモンが必要である。

```bash
sudo pigpiod
pigs t
```

`pigs t`で数値が返ることを確認する。通常のPCシミュレーションではpigpioを起動しない。

## 5. 浮かせた状態で統合動作を確認する

現行の`ellipse_run`には、エンコーダだけ、操舵だけ、中立だけを選択する試験モードがない。
`use_hardware = True`で起動すると、約`1.0 s`の中立出力後、操舵とESCへの駆動出力を開始する。

この制約を理解し、駆動輪を浮かせ、物理電源遮断を準備してから次へ進む。

```python
use_hardware = True
```

初期姿勢をコードの座標系に合わせる。

- 初期位置: 楕円最下部の`(0 m, 0 m)`
- 初期方位: 正のX方向、`0 rad`
- 楕円中心: `(0 m, 1.2 m)`

`ellipse_run`ディレクトリから実行する。

```bash
cd scripts/ellipse_run
python3 run_ellipse.py
```

実行直後に次を確認する。

- 約`1.0 s`のアーミング待機中、操舵とESCが中立である。
- タイヤの回転方向が車体の前進方向と一致する。
- 操舵方向が参照経路の方向と一致する。
- エンコーダ距離が増加する。
- `Ctrl-C`で操舵とスロットルが中立になり、処理が終了する。
- 終了後に`pose_log.csv`が保存される。

異音、機械的干渉、予期しない全開出力、逆回転、操舵方向の逆転、距離の減少があれば、
物理電源を切って原因を確認する。

## 6. 床上で低速走行を確認する

現在の楕円はX方向が`-2.0 m`から`2.0 m`、Y方向が`0 m`から`2.4 m`の範囲にある。
車体寸法、追従誤差、停止距離を含む十分な余裕を確保する。

床上確認では次の順に評価する。

1. 車体を初期位置と初期方位へ正確に置く。
2. 物理電源遮断を担当する人を配置する。
3. 1周だけ実行する。
4. 走行終了後、実際の軌跡と`pose_log.csv`の推定軌跡を比較する。
5. 操舵中立、タイヤ直径、ホイールベース、最大操舵角、スロットル値を必要に応じて校正する。

現行実装では、実機走行中の`TARGET_SPEED = 0.4 m/s`は速度制御に使われない。
実機では`THROTTLE_DRIVE_US`を固定出力するため、実速度はESC、モーター、バッテリー、
路面および負荷に依存する。`0.4 m/s`で走ると仮定しないこと。

## 停止処理

制御ループ中の`Ctrl-C`または例外では、`finally`節が次を実行する。

1. 操舵を`STEER_NEUTRAL_US`へ戻す。
2. ESCを`THROTTLE_NEUTRAL_US`へ戻す。
3. エンコーダ割り込み監視を解除する。
4. pigpio接続を終了する。
5. ログと軌跡画像を保存する。

ソフトウェア停止だけに依存せず、異常時は物理電源遮断を優先する。

## 現行実装の制約

- LiDARとカメラは使用しない。
- 位置推定はエンコーダ距離と指令操舵角だけを使う。
- タイヤのスリップ、操舵校正誤差、サーボの遊び、車体のバックラッシュが累積誤差になる。
- 実速度のフィードバック制御はない。
- 段階的な実機試験モードはない。
- `LidarMCLLocalizer`は未実装である。

段階的な試験を`ellipse_run`だけで完結させる場合は、将来の実装として、
中立出力、操舵のみ、エンコーダのみ、低速駆動、全体走行を明示的に選べる試験モードを追加する。
その場合も`use_hardware = False`を既定値として維持し、すべての終了経路で中立出力を行う。
